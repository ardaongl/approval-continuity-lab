# Concurrency and crash recovery (normative)

## Locking and linearization

Every DB command uses an independent SQLite connection and BEGIN IMMEDIATE before reading authoritative state. The underlying writer/read behavior is documented in [SQLite transactions](https://www.sqlite.org/lang_transaction.html) and [rollback-journal locking](https://www.sqlite.org/lockingv3.html). SQLite serializes writers. The lock is held through current context/expiry/target checks, effect, execution row, consumed transition and commit. No unlocked read-then-write authorization. The linearization order for observable effects/revocation is transaction commit order; a lock-holder that crashes/rolls back never wins.

DELETE journal avoids a WAL checkpoint lifecycle in this small lab. [cache_spill=OFF](https://www.sqlite.org/pragma.html#pragma_cache_spill) prevents dirty-page spill from acquiring an EXCLUSIVE lock before the precommit observer; this makes the independent old-state reader at crash point A a valid bounded observation. Preflight must verify these SQLite settings/capabilities. FULL synchronization requests SQLite's durability facilities; supported local filesystem/process-crash assumptions only. Foreign keys enabled per connection. Read report state in the same transaction; emit after commit. Busy waits ≤2000 ms plus OS scheduling overhead; no application retry loops.

Revoke first: reviewer transaction commits approved→revoked; later execute sees APPROVAL_REVOKED, no effect/execution. Execute first: service update + result + consumed commits; later revoke returns TOO_LATE, no revoked transition. A repeated execution with the same ID still retrieves history.

Target writer first: admin service update increments revision; execute supersedes with TARGET_REVISION_CHANGED. Execute first: target writer blocks; deploy commits one increment; writer using old expected revision then gets REVISION_CONFLICT. No target mutation can interleave between revision check and effect. No guarantee for out-of-band raw SQL or external targets.

## Observer seam and deterministic schedules

Production Lab accepts optional Observer; default does nothing. Public CLI cannot select observers, failpoints or executable callbacks. Scenario workers expose only fixed D01–D14 worker roles. Observer has no connection/SQL handle and cannot change clock/results/decisions. Fixed notifications: before_begin, after_begin, after_checks, before_commit (all proposed writes complete but commit not called), after_commit_before_response. Passing an Observer does not change transaction boundaries or skip validation. Observer exceptions before commit roll back; exceptions after commit cannot undo effects. An operator-supplied Observer is trusted instrumentation, not untrusted extension support.

Test/scenario coordinator uses pipes (separate from stdout/stderr) and explicit ready/release/ack messages. Each rendezvous has a 5-second monotonic scheduling deadline; child lifetime bound 15 seconds, cleanup bound 5 seconds. Timeout is test/scenario failure, never a skipped/pass race. Close unused pipe ends; on any failure terminate/reap children, remove temp state only after handles close. No sleep-based correctness oracle or polling for a guessed time. Wait APIs with bounded timeouts are allowed.

D06: start two processes with independent connections, fixed execution IDs x-a/x-b. Both signal before_begin. Release A; A acquires lock and signals after_begin; release B to attempt BEGIN while A holds; release A to commit; B proceeds and refuses consumed grant. Require both completions and raw state. Repeat with release order reversed in tests. Same-ID variant retrieves result once. Additionally calibrate real contention: while A holds after_begin, B performs a full normal BEGIN attempt and reports STORAGE_BUSY after the fixed2000ms wait; only after that acknowledgment release A, then issue B's explicit second execution command to observe consumption/replay. This is coordinator-directed separate work, not an automatic application retry or changed busy_timeout. Capture the actual SQLITE_BUSY code. The successful waiting-race case alone cannot prove the scheduler reached SQLite while A held its lock. A non-ordered stress case may be added but cannot replace ordered schedules.

D07: run both serial commit orderings using the same before_begin/after_begin/precommit acknowledgments. D08 target race similarly forces writer-first and executor-first. Verify a worker waiting on BEGIN has not reached after_begin by a coordinator probe/explicit protocol state, not by sleeping. Core correctness oracle is final raw state plus returned results; no claim of precise scheduler timing.

## Crash points

A: after_checks and all service/execution/consumed writes, at before_commit. Worker signals ready and blocks on private release pipe. Coordinator independently reads the DB (writer reserved lock permits readers), observes old committed state, sends SIGKILL to the held process, waits/reaps it, then opens a fresh SQLite connection to trigger recovery. Expected: approval approved; target old artifact/revision; no execution; no consumed transition; transaction's floor advance rolled back. Retry identical execution at a valid time commits one effect.

B: at after_commit_before_response, worker signals commit acknowledged via private pipe and blocks before report serialization/delivery. Coordinator reads all durable rows, kills/reaps worker, opens fresh connection and retries same execution. Expected: consumed, new artifact/revision, one stored result; exact retry returns that result with replayed=true and zero additional update. Repeat after expiry/current revision change/clock regression to demonstrate history lookup. The later admin drift update itself may change target, but retry adds no further effect.

SIGKILL is POSIX-specific and intentionally produces OS termination, not a product exit code. The test checks coordinator evidence, not a fabricated graceful crash report. Installed scenario runner reports a successful experiment after verifying recovery. No hidden failpoint env vars; scenario workers use the same observer seam and mediator entry point as API tests. Tests must also exercise a normal process without instrumentation.

## Durable independent observations

Raw SQL reads on fresh connections verify proposals.status/status_reason, services.artifact_digest/revision, decisions immutable expiry, executions count/request/result, transition sequence and meta floor. Never derive expected state from the mediator report or production helper. Save coordinator transcript/child exits and snapshots in ignored evidence. COMMIT IO error can have unknown outcome; the public command must direct reconciliation by execution ID, not assert rollback. Recovery guarantees assume a valid SQLite database/local filesystem; corruption is an error fixture, not automatically repaired.

COMMIT SQLITE_BUSY with connection still in_transaction is a known noncommit: explicitly ROLLBACK, close, return STORAGE_BUSY/no effect/no floor advance. Do not retry COMMIT in an unbounded loop. Any other COMMIT failure without proven rollback retains effect_status unknown and must be reconciled through a fresh execution lookup; do not overwrite the result or retry with a new identity. Independent raw readers must close before releasing a writer to commit.
